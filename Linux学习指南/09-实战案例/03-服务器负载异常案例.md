# 服务器负载异常案例

> 模块：实战案例
> 更新时间：2026-05-19

---

## 一、问题发现

### 监控告警

```bash
# 收到告警: 服务器负载飙升
# 监控显示: load average: 28.50, 25.20, 18.30
# 服务器配置: 8核CPU, 32GB内存

# 第一步: 确认负载
uptime
# 10:30:00 up 45 days, load average: 28.50, 25.20, 18.30

# 负载远超CPU核数(8核)，系统严重过载
# 负载持续上升，问题正在恶化
```

### 初步诊断

```bash
# 查看CPU使用
top -b -n 1 | head -5
# %Cpu(s): 45.2 us, 12.3 sy, 0.0 ni, 5.8 id, 35.2 wa, 0.5 hi, 1.0 si
# wa(IO等待)高达35%，说明IO是主要瓶颈

# 查看内存
free -h
# 总内存使用正常，Swap未使用

# 初步结论: IO瓶颈导致负载飙升
```

---

## 二、IO瓶颈定位

### 磁盘IO分析

```bash
# 查看磁盘IO状态
iostat -x 1 5
# Device   r/s    w/s   rkB/s  wkB/s  await  svctm  %util
# sda     150.00  800.00  2400  64000   85.20   1.20  98.50

# sda磁盘%util达到98.5%，await高达85ms
# 确认是磁盘IO严重过载

# 找出IO消耗进程
iotop -o -b -n 3
# Total DISK READ: 150.00 M/s | Total DISK WRITE: 800.00 M/s
# PID    PRIO  USER     DISK READ  DISK WRITE  COMMAND
# 12345  be/4  mysql    120.00 M/s  600.00 M/s  mysqld
```

### 数据库IO分析

```bash
# MySQL进程IO消耗最大
# 查看MySQL状态
mysql -e "SHOW PROCESSLIST;"
# 发现大量慢查询

# 查看慢查询日志
tail -100 /var/log/mysql/slow.log
# 发现大量全表扫描查询

# 查看表状态
mysql -e "SHOW TABLE STATUS LIKE 'orders';"
# 数据量: 5000万行，索引未优化
```

---

## 三、问题根因

### 分析慢查询

```bash
# 分析慢查询日志
mysqldumpslow -s t -t 10 /var/log/mysql/slow.log
# Top慢查询:
# 1. SELECT * FROM orders WHERE status='pending' ORDER BY created_at
#    平均耗时: 45秒
#    扫描行数: 5000万行

# 查看执行计划
mysql -e "EXPLAIN SELECT * FROM orders WHERE status='pending' ORDER BY created_at;"
# type: ALL (全表扫描)
# rows: 50000000
# Extra: Using filesort

# 问题定位:
# 1. status字段没有索引
# 2. ORDER BY created_at导致filesort
# 3. SELECT * 导致回表
```

## 四、解决方案

### 紧急处理

```bash
# 1. 杀掉慢查询进程
mysql -e "SHOW PROCESSLIST;" | grep "Query" | awk '{print $1}' | \
  xargs -I {} mysql -e "KILL {};"

# 2. 限制MySQL连接数
mysql -e "SET GLOBAL max_connections = 100;"

# 3. 监控IO恢复
watch -n 1 'iostat -x | grep sda'
# 等待%util下降到正常水平
```

### 添加索引

```bash
# 添加复合索引
mysql -e "ALTER TABLE orders ADD INDEX idx_status_created (status, created_at);"

# 查看索引创建进度
mysql -e "SHOW PROCESSLIST;" | grep "alter\|index"

# 验证索引效果
mysql -e "EXPLAIN SELECT * FROM orders WHERE status='pending' ORDER BY created_at;"
# type: ref
# rows: 100000
# 索引生效，扫描行数从5000万降到10万
```

### 优化SQL

```bash
# 优化查询语句
# 原始SQL
# SELECT * FROM orders WHERE status='pending' ORDER BY created_at;

# 优化后
# SELECT id, order_no, amount, created_at 
# FROM orders 
# WHERE status='pending' 
# ORDER BY created_at
# LIMIT 1000;

# 查看优化效果
time mysql -e "SELECT id, order_no, amount, created_at FROM orders WHERE status='pending' ORDER BY created_at LIMIT 1000;"
# 执行时间: 0.5秒 (原45秒)
```

## 六、经验总结

### 问题原因

```bash
# 根本原因: 数据库查询缺少索引，导致全表扫描
# 触发条件: 数据量增长到5000万行后，全表扫描耗时剧增
# 影响范围: 所有依赖该查询的接口响应超时
# 持续时间: 约30分钟
```

### 改进措施

```bash
# 1. SQL审核机制
# 上线前必须进行SQL Review
# 使用EXPLAIN分析执行计划
# 禁止SELECT *，必须指定字段

# 2. 索引规范
# WHERE条件字段必须有索引
# ORDER BY字段纳入索引
# 定期检查未使用的索引

# 3. 监控完善
# 慢查询监控告警
# 数据库连接数监控
# 磁盘IO监控告警

# 4. 容量规划
# 定期评估数据增长
# 提前进行分库分表
# 归档历史数据
```

### 排查检查清单

```bash
# 5. 分析应用日志/慢查询
# 6. 定位根因并修复
# 7. 验证系统恢复
# 8. 总结改进措施
```
