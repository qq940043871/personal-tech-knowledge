阶段一：浏览器端 —— 请求的诞生

用户操作触发请求，浏览器完成 DNS、TCP、TLS 一系列准备工作

1.1 URL 输入与解析

用户在地址栏输入 https://www.example.com/api/order/create，浏览器首先解析这个 URL：

协议httpsHTTPS = HTTP + TLS，默认端口 443

端口443（默认）HTTPS 默认 443，HTTP 默认 80

1.3 TCP 三次握手

1 客户端 → SYN (seq=x) → 服务器
2 客户端 ← SYN+ACK (seq=y, ack=x+1) ← 服务器
3 客户端 → ACK (ack=y+1) → 服务器 ✓

为什么是三次，不是两次或四次？

两次无法防止历史连接（已失效的 SYN 到达服务端，服务端误以为新连接）；四次则冗余——第三次握手时双方已确认收发能力正常。

1.4 TLS / SSL 握手（HTTPS）

ClientHello —— 发送支持的加密套件
ServerHello + 数字证书
验证证书 → 生成对称密钥
加密通信就绪 ✓

TLS 1.3 优化

TLS 1.3 将握手从 2-RTT 优化至 1-RTT，大幅降低连接延迟。还支持 0-RTT 会话恢复。

面试高频追问

Q1: DNS 劫持是什么？如何防范？

DNS 劫持指运营商或攻击者篡改 DNS 解析结果，将用户导向错误 IP。

HTTPDNS：通过 HTTP 协议直连可信 DNS 服务器
DNSSEC：对 DNS 响应做数字签名校验
DoH / DoT：加密 DNS 请求，防中间人篡改

Q2: 七层负载均衡能做什么四层做不到的？

能力L4（四层）L7（七层）
按 URL 路径转发
按 Cookie / Session 保持
内容压缩与缓存
SSL 卸载
请求改写与重定向
WebSocket 支持

Q3: API 网关和服务网格（Service Mesh）有什么区别？

API 网关

管理南北向流量（外部 → 内部）
处理鉴权、限流、协议转换

Service Mesh

管理东西向流量（服务间调用）
处理服务发现、熔断、可观测性

两者互补，而非替代关系。

Q4: 一个请求从发起到响应，通常经过多少个中间环节？

典型微服务架构下约 15~25 个环节。若涉及跨服务调用（如订单 → 库存 → 支付），链路更长。这也解释了为什么分布式链路追踪（APM）在生产环境中不可或缺。

总结

一个看似简单的 HTTP 请求，从浏览器出发到达后端服务器，经历了 15+ 个关键环节：

DNS 解析 域名 → IP
TCP + TLS 安全通道
防火墙 / WAF 安全防线
负载均衡 流量分发
API 网关 统��入口
服务发现 定位实例
中间件链 认证/日志/熔断
业务代码 Controller → DB

理解这条链路，是成为架构师的基本功。每个环节都可能成为性能瓶颈或故障点，排查问题时需逐段定位。
