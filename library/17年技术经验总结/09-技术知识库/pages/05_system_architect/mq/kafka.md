# Kafka 从零理解 - 架构师学习笔记

> 定位:原理层图文,与《17年技术经验总结/07-消息中间件/03-Kafka实战》(Spring Boot 集成与生产案例)互补。

## 一、Kafka 的本质:分布式的"提交日志"

```
Topic: order-events
Partition 0: [0][1][2][3][4][5]  ←─ append-only,只追加
Partition 1: [0][1][2][3]        ←─ 每条消息一个递增 offset
Partition 2: [0][1][2][3][4]
      ▲
      └── 分区 = 并行度单位 + 顺序性单位 + 副本单位
```

三条铁律从这张图推出:

1. **分区是并行度的最小单位**——消费者数 ≤ 分区数,多了就空转
2. **顺序只在分区内保证**——全局有序必须单分区(牺牲并行)
3. **offset 是消费位置的账本**——消费完不删数据,靠 offset 推进;"重放"就是重置 offset

## 二、为什么 Kafka 快(面试高频,逐条对应机制)

| 手段 | 原理 |
|---|---|
| 顺序写磁盘 | 追加写日志文件,磁盘顺序写 ≈ 内存随机写速度 |
| 页缓存 | 读写都走 OS page cache,不自建缓存,JVM 压力小 |
| 零拷贝 | `sendfile`:数据从页缓存直达网卡,跳过用户态两次拷贝 |
| 批量 + 压缩 | 生产者攒 batch(linger.ms/compression.type),网络与 IO 摊薄 |
| 稀疏索引 | 按 offset 建稀疏索引,定位消息 O(logN) |

## 三、消费者组:两种模型的统一

```
组A(订单处理): C1 ← P0,P1    C2 ← P2        (组内:竞争,分摊分区)
组B(数据仓库): C1 ← P0,P1,P2                 (组间:广播,各自全量)
```

- 每个分区同一时刻只归组内**一个**消费者 → 组内天然不重复消费
- 消费者增减触发 **Rebalance**,分区重新分配——Rebalance 期间整组停止消费(频繁 Rebalance 是经典生产事故,诱因:消费超时、心跳丢失、扩缩容)

## 四、副本与 ACK:可靠性的核心权衡

```
Partition P0: Leader(broker1) ── follower: ISR{broker2, broker3}
                                 ISR = 与 Leader 保持同步的副本集合
```

| acks | 含义 | 丢失风险 | 吞吐 |
|---|---|---|---|
| 0 | 发出去就算成功 | Leader 挂即丢 | 最高 |
| 1 | Leader 写入即成功 | Leader 挂且未同步到 follower 会丢 | 中 |
| all(-1) | ISR 全部写入才成功 | 配合 `min.insync.replicas=2` 基本不丢 | 最低 |

生产推荐组合:`acks=all` + `min.insync.replicas≥2` + `retries>0` + `enable.idempotence=true`(生产者幂等,防止重试导致分区内重复/乱序)。

## 五、Exactly-Once 是怎么做的

```
① 生产端幂等:PID + 序列号,Broker 去重 → 单分区内不重不乱
② 事务:多分区写入原子提交(transactional.id),read_committed 隔离读
③ 消费端:offset 与业务处理绑在同一事务/或消费端幂等
```

工程现实:**跨系统(如 DB)的 Exactly-once 仍靠消费端幂等**(唯一键/去重表),Kafka 事务只保证"Kafka 内部"的原子性。

## 六、顺序性与可靠性怎么同时要

```
同一订单的消息 → 按订单ID分区(send 指定 key)→ 分区内自然有序
                    │
                    └─ 若该分区重试乱序 → 开启幂等后 Broker 保证分区内不乱序
```

- `max.in.flight.requests.per.connection>1` 时,未开幂等可能乱序;开幂等后 Broker 会拒绝序列号跳变,保证不乱
- 消费端多线程处理会再次打乱顺序 → 按 key 哈希到内存队列,同 key 串行(见经验笔记"顺序消费实现")

## 七、消息积压的原理与处理思路(速查)

```
积压 = 生产速率 > 消费速率
   → 消费端扩容(上限=分区数)
   → 分区不够就加分区(注意:key 分区的既有映射会变)
   → 临时"垫层"消费者把消息批量转储到新 Topic(分区更多)再并行消费
```

原理层对应:消费者数受限于分区数(第二节铁律1),所以扩分区是治本、扩消费者是治标。
