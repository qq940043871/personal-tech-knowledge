# 消息队列是怎么工作的 - 架构师学习笔记

> 定位:从零理解消息队列的原理层图文,与《17年技术经验总结/07-消息中间件》的经验实战笔记互补。

## 一、没有消息队列时,问题出在哪

三个典型场景,理解 MQ 解决的三类问题:

```
场景A:下单后要发短信、发优惠券、更新推荐……
  同步调用:下单接口耗时 = 各步骤耗时之和,任何一个下游挂了,下单就失败
  → 问题:【耦合】主流程被下游拖累

场景B:秒杀开始,1秒涌入 10 万请求,数据库只能扛 5000/s
  → 问题:【削峰】流量直接打到存储层,系统被打垮

场景C:订单服务要同时通知库存、物流、积分三个团队的服务
  → 问题:【异步】主流程没必要等它们做完
```

消息队列的本质:**把"现在必须做完"改成"先记下来,慢慢做"**——用一条持久化的消息序列,在 produced 与 consumed 之间加一层缓冲。

## 二、两种消息模型

### 1. 点对点(Queue 模型)

```
生产者 ──▶ [ 队列: m1 m2 m3 ] ──▶ 消费者A
                                 ──▶ 消费者B      (一条消息只被其中一个消费)
```

- 多个消费者竞争消费,消息不重复,天然适合**任务分发**

### 2. 发布订阅(Topic / Pub-Sub 模型)

```
             ┌── 订阅者1(库存服务)  收到 m1,m2,m3
生产者 ──▶ [ Topic ]──┼── 订阅者2(物流服务)  收到 m1,m2,m3
             └────────── 订阅者3(积分服务)  收到 m1,m2,m3
```

- 每个订阅者各自拿到全量消息,适合**事件广播**
- Kafka 的 Consumer Group 是两种模型的统一:组内竞争(点对点)、组间广播(发布订阅)

## 三、投递语义:消息到底会不会丢/重复

| 语义 | 含义 | 代价 |
|---|---|---|
| At-most-once | 最多一次,可能丢 | 发完就忘,性能最好 |
| At-least-once | 至少一次,可能重复 | 需要确认+重试,最常用 |
| Exactly-once | 恰好一次 | 需要幂等/事务,成本最高 |

直观理解"为什么 Exactly-once 难":

```
消费者处理完消息 → 还没来得及提交 offset → 宕机
重启后从旧 offset 重新消费 → 消息被处理了两次
```

结论:**可靠投递 = 确认机制 + 重试,必然引入重复;工程上的 Exactly-once 几乎都是"至少一次 + 消费端幂等"**(幂等手段:唯一业务ID去重、数据库唯一键、Redis setnx)。

## 四、消息顺序:为什么"全局有序"很贵

- 队列要保证全局有序,就必须串行读写 → 吞吐能力被锁死
- 主流做法:**分区内有序**——同一业务键(如同一订单ID)的消息路由到同一分区/队列,分区间并行

```
订单A的消息 ──hash(A)──▶ 分区0: A1 → A2 → A3   (分区内严格有序)
订单B的消息 ──hash(B)──▶ 分区1: B1 → B2       (与分区0互不干扰)
```

顺序性被破坏的两个经典坑:消费者组 Rebalance 后分区易主、重试队列把后到的消息先消费。

## 五、主流消息中间件选型

| 维度 | RabbitMQ | Kafka | RocketMQ |
|---|---|---|---|
| 模型 | AMQP(Exchange 路由) | 分区日志 | Topic/Queue |
| 吞吐 | 万级/秒 | 百万级/秒 | 十万级/秒 |
| 延迟 | 微秒~毫秒级,低 | 毫秒级(批量换吞吐) | 毫秒级 |
| 顺序 | 队列内有序 | 分区内有序 | 分区内有序 |
| 事务 | 轻量(发送方确认) | 强(事务消息 + 幂等) | 事务消息(半消息) |
| 典型场景 | 业务解耦、路由复杂、低延迟 | 日志/埋点/大吞吐流处理 | 电商交易、事务消息 |
| 语言/运维 | Erlang,运维简单 | Scala/Java,集群较重 | Java,阿里系生态 |

选型口诀:**要路由灵活和低延迟选 RabbitMQ,要吞吐和回溯选 Kafka,要事务消息选 RocketMQ**(团队技术栈也是重要权重)。

## 六、一条消息的生命周期(全链路可靠性总览)

```
生产者                    Broker                      消费者
  │ confirm/ack ①           │ ②持久化(刷盘/副本)          │
  ├────────────────────────▶│───────────────────────────▶│
  │                          │        ③手动 ack / 提交 offset
  ◀── 失败则重试/落库补偿 ─────┤         (失败则重新投递 → 死信)
```

三个环节都可能丢消息,也都有对应的确认手段——细节见同目录 [rabbitmq.md](rabbitmq.md) 与 [kafka.md](kafka.md)。
