How a SQL Query is Executed Inside a Database

核心问题：当你敲下 SELECT * FROM users WHERE age > 25 ORDER BY name LIMIT 10; 并按下回车后，数据库内部到底发生了什么？本文以 MySQL（InnoDB）为例，逐层拆解整个过程。

整体架构概览

MySQL 可以分为 Server 层和存储引擎层两部分。Server 层负责连接、分析、优化、执行等通用功能；存储引擎层负责数据的实际存储和读写。

①连接器

连接器负责与客户端建立 TCP 连接、身份认证、权限校验。

TCP 三次握手

客户端通过 TCP 与 MySQL 服务端（默认 3306 端口）建立连接。

身份认证

校验用户名、密码、连接来源 IP 是否在授权范围内。

权限读取

从权限表读取该用户拥有的权限，缓存到连接对象中。后续操作基于此快照判断。

连接管理

空闲连接超过 wait_timeout（默认 8 小时）自动断开。长连接累积内存可能导致 OOM。

注意：权限在连接建立时读取并缓存。如果中途用 GRANT 修改了权限，已存在的连接不会生效，需要重新连接。

⓪查询缓存 (MySQL 8.0 已移除)

MySQL 8.0 之前，SQL 语句会先以 key-value 的形式被缓存在内存中。如果命中缓存，直接返回结果，不走后续流程。但由于缓存的失效粒度太粗（表上任何写操作都会清空整张表的所有缓存），在高并发写入场景下缓存命中率极低，反而成为性能瓶颈，因此在 8.0 版本中被彻底移除。

②分析器 —— 词法分析 & 语法分析

分析器负责将 SQL 文本"翻译"成数据库能理解的内部数据结构 —— 语法树（AST）。

词法分析（Lexical Analysis）

将 SQL 字符串拆解为有意义的 Token（记号）。

输入 SQL：

SELECT * FROM users WHERE id = 1;

语法分析（Syntax Analysis）

根据 MySQL 定义的语法规则，将 Token 序列组织成一颗抽象语法树（AST, Abstract Syntax Tree）。

如果 SQL 语法有误（例如 SELECT * FORM users 把 FROM 拼错），MySQL 会在这一步抛出错误： ERROR 1064: You have an error in your SQL syntax。

SELECT_STMT

└── table_ref: users
    └── WHERE
        └── condition: id = 1

③优化器 —— 选择最优执行方案

优化器是数据库的大脑。在语法树的基础上，它决定使用哪个索引、以什么顺序 JOIN、是否做条件下推等关键策略，生成一个代价最低的执行计划。

索引选择

基于统计信息（数据量、区分度、索引长度）评估每种索引的扫描行数。同样一条 SQL，id > 1000 可能走索引，id > 1（覆盖全表大部分数据）可能直接全表扫描更快。

JOIN 顺序选择

多表 JOIN 时，决定以哪张表作为驱动表。原则是小表驱动大表，减少扫描行数。优化器通过 Nested-Loop Join + 代价估算来决定最优 Join 顺序。

条件下推

索引条件下推（ICP, Index Condition Pushdown）：将 WHERE 条件的过滤下推到存储引擎层，减少回表次数。5.6 版本引入。

查询改写

优化器会自动进行查询改写：子查询转 JOIN、IN 转 EXISTS、常量表达式折叠（1+2 → 3）、外连接转内连接等。

查看执行计划：EXPLAIN

使用 EXPLAIN 可以查看优化器生成的执行计划：

优化器核心策略

1
基于成本的优化（CBO, Cost-Based Optimization）： 优化器根据统计信息估算每种执行计划的 CPU、IO 代价，选择总代价最小的方案。MySQL 使用 ANALYZE TABLE 更新统计信息。
2
MRR（Multi-Range Read，多范围读取）： 将二级索引的随机 IO 转化为顺序 IO，通过先收集主键再排序后批量回表，减少磁盘随机读的磁头移动次数。
3
BNL（Block Nested-Loop Join）： 当 JOIN 没有可用索引时，将驱动表的数据分批读入 Join Buffer（默认 256KB），然后与被驱动表进行全表扫描匹配。8.0.20 后被 Hash Join 替代。

④执行器

执行器拿到优化器生成的执行计划后，开始逐行调用存储引擎的接口来执行。执行器本身不存储数据，它通过存储引擎提供的 Handler API 来读写数据。

执行流程（伪代码） 

-- SQL: SELECT * FROM users WHERE age > 25

// 执行器的伪代码逻辑（无索引时）
for (row in users_table) {          // 调用引擎接口，逐行读取，全表扫描
    if (row.age > 25) {             // 在 Server 层判断
        send_to_client(row);         // 满足条件，发送给客户端
    }
}

// 有索引时
for (index_row in idx_age) {        // 遍历索引
    if (index_row.age > 25) {
        // 索引条件下推：age > 25 在引擎层判断
        row = engine.fetch_by_primary_key(index_row.pk);
        send_to_client(row);
    }
}

⑤存储引擎 —— 数据到底在哪

存储引擎负责数据的物理存储和读写。MySQL 是插件式架构，支持多种引擎，最主流的是 InnoDB（5.5.5 起成为默认引擎）。

InnoDB

  • 支持事务（ACID）
  • 行级锁 & MVCC
  • B+ 树索引（聚簇索引）
  • 支持外键
  • 崩溃恢复（Redo Log）

MyISAM

  • 不支持事务
  • 表级锁
  • 全文索引（5.6 前）
  • 不支持外键
  • 适合只读 / 极少写场景

InnoDB 内部的读写路径（以 SELECT 为例）

1
Buffer Pool 检查：先检查数据页是否已在内存的 Buffer Pool 中。命中 → 直接返回。
2
磁盘读取：未命中 → 从磁盘（.ibd 文件）读取对应的数据页，先载入 Buffer Pool。
3
MVCC 可见性判断：根据事务 ID 和 Read View 判断当前事务能看到哪个版本的数据。
4
返回数据：将满足条件的行返回给 Server 层的执行器。

重要补充：Redo Log 与 Binlog

以上讲的是查询（SELECT）的执行流程。如果是更新语句（INSERT / UPDATE / DELETE），还会涉及两个关键日志，它们是 MySQL 实现高可靠性的基石。

Redo Log（重做日志） InnoDB 特有

  • 物理日志：记录"在某个数据页上做了什么修改"
  • WAL 机制：先写日志再写磁盘
  • 循环写：固定大小（默认 2 组 × 4 文件），循环覆盖
  • 用途：崩溃恢复（Crash Recovery）

Binlog（归档日志） Server 层

  • 逻辑日志：记录 SQL 语句的原始逻辑
  • 追加写：无限追加，不会覆盖
  • 用途：主从复制、数据恢复
  • 格式：STATEMENT / ROW / MIXED

UPDATE 语句的二阶段提交

为保证 Redo Log 和 Binlog 逻辑一致，更新语句采用二阶段提交：

1
Prepare 阶段：写 Redo Log，状态标记为 prepare。
2
写 Binlog：记录本次修改的 Binlog。
3
Commit 阶段：Redo Log 状态改为 commit，事务完成。

总结

阶段 负责组件 核心职责 输出
① 连接 连接器 TCP 握手、身份认证、权限读取 连接对象
② 分析 分析器 词法分析 → 语法分析 → AST 抽象语法树
③ 优化 优化器 索引选择、JOIN 顺序、条件下推 执行计划
④ 执行 执行器 按计划调用引擎接口，逐行操作 结果集
⑤ 存储 存储引擎 Buffer Pool、B+ 树、MVCC、Redo Log 磁盘文件 (.ibd)

面试常见追问

  • Q: "为什么 MySQL 8.0 移除了查询缓存？" → 缓存失效粒度太粗，一张表有任何写操作就清空全表缓存，高并发写入场景下命中率极低且维护开销大。
  • Q: "优化器选错索引怎么办？" → 使用 FORCE INDEX 强制指定，或调整统计信息 ANALYZE TABLE，或使用 optimizer_switch 参数调整优化器行为。
  • Q: "为什么要用二阶段提交？" → 防止 Redo Log 和 Binlog 不一致导致崩溃恢复后主从数据不一致。
  • Q: "type=ALL 一定慢吗？" → 不一定。如果表很小（如几百行），全表扫描反而比走索引更快（减少回表开销）。
